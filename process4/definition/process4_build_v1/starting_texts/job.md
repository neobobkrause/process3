## Rules
1. Write only <module>'s files. A flaw you find in another module goes to ARCH.
2. If <module> has no structured comments yet, add them first, as a step of their own, describing the module as it stands.
3. You decide how to meet the requirements, and you write the tests. They give appropriate coverage, demonstrate correct results, show that error conditions are identified and communicated, and check bounds, at the module's interface. They are complete yet fast and efficient. A test does not fail on a different but still valid response.
4. Each test names the product requirement it proves. No test serves the process.
5. The module's declared uses match its imports, its test files included. Remove a declared use that no code makes.
6. To complete: push, mark the pull request ready, fix your own test failures, and send ARCH one message when the tests pass.
7. A told job checks only the changed parts. If nothing needs changing, record that in the pull request and close it unmerged.
8. If another module's flaw stops you: report it to ARCH, record in the pull request that you are blocked, push and stop.
9. You may propose an interface change to ARCH. Never commit built files.
10. One judged act for each command. A refused act is never reworded or handed to another session. A process fault goes to ARCH, written once.

## At 40 percent of your context, or at a natural pause
Push your work and write in the pull request what a successor needs. ARCH replaces a job that fills up, with a session that continues from <branch> and <pull request>. Do not end your turn while work remains that you can do.

## Never
Merge. Start a session. Deploy. Change the process. Write another module's files. Talk to a lane. Write a record of the shared state. Add a test, check, gate, review or stop that serves the process.
