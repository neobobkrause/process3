# process3
The Process3 tool and its workflows. Built in Phase 1 of the Process3 Build Plan.

- `tool/p3.mjs`: the tool, one program run from a pinned clone (`node .process/tool/p3.mjs <command>`). No dependencies.
- `setup/conditions.json`: the setup a product needs before a job starts, one entry per condition (what, why, value, who sets it, how it is read or that it is confirmed once on the onboarding page).
- `setup/DEVELOPER.md`: the steps only the repository's owner can take, each with why, the clicks on github.com, how BOB confirms it, and the setup-list entry it sets.
- `schema/ledger-entry.schema.json`: the ledger entry (REC-9). A product keeps one file per entry in `process/ledger/<id>.json`.
- `.github/workflows/ci.yml`: this repository's own check: the tool's tests and the record check.
- A job's pull request: the gate runs its own module's suite, then the product's smoke list, `smoke` in `process/config.json` (`{"files": [test files], "seconds": <cap, default 120>}`, read at the base): each listed file not under the job's own test paths runs by the module whose tests hold it, within the cap in all (base-red has its own budget, as the suite's does; once the cap is spent the files left are one finding), the cheap catch for a break across modules (Bob, 4 Nov: running users' suites cost +7.6 min median per job gate and caught none of 20 refuted claims). A smoke test red at the base too is reported in the row's `smoke.base_red` and owed as the suite's base-red is, not blocking; any other failure, or a listed file no module's tests hold, is a finding. The receipt claims only the job's own suite.
- The tranche into main: the gate runs a module's suite only when one of the module's files was last changed on the tranche by something other than a job merge whose gate was green, and verified, on the merged result (a plain pull request, a direct commit, a conflict resolved bringing main in); every other module file names the job PR whose gate tested it, in the log and in the row's `through`. A covered module's suite still runs when a module it uses (at any depth) changed on the tranche after its job merge, and a file in two modules' paths is covered by neither's job. A tranche of 30+ modules, whose suites in sum would pass the gate job's 45-minute cap, no longer runs them all (PR 89's report, 4 Nov). Coverage reads each merged job PR's gate run and its gate-row artifact (kept 90 days): where either cannot be read, the suite runs. GitHub lists no pull request on a merged PR's runs (copy, 4 Nov), so the run is bound to the merged PR by what GitHub keeps: the process gate, event `pull_request`, green, on `job/<id>` in this repository, at the PR's head or an earlier commit of it, with a base on the tranche at or before the commit it merged into, and an artifact holding the same row (its scope and `after` too); and every pull request ever opened from `job/<id>` must be into the tranche and never have had its base changed (a PR from the branch into another base runs that base's workflow file; the pulls API shows only the current base, so each PR's issue events are read for `base_ref_changed`), else, or when either cannot be read, the module's suite runs. The gate's job gate runs at the tranche's pin, not main's, for the tranche into main (same repository, base the default branch) when that pin descends from main's on process3's own main or tranche, read from the clone of the base's `process_repo`; otherwise at main's. Job post stays at the base's pin.
- `shims/`: the workflows a product carries: `process-gate.yml` (the required check "gate": the gate and the record check on every pull request, at the base's process pin (the tranche into main: the tranche's, when it descends from main's on process3), on a read-only token; then job "post", which runs no product code, posts the gate comment from the run's gate-row artifact). If job post fails to post, the required check stays green; that is accepted, because merge refuses a job without a verified gate row (review of PR 13). The legacy path for pins older than the two-job gate is gone from the shim; `tool/p3.mjs` keeps its `p3-capability: gate-no-post` line until every product carries this shim, since older shims grep the pinned tool for it.
- `shims/process-record.yml`: the record check on every push to main and to the branch named `tranche`.
- `ranges.json`: the product sizes (`p3 size` figures) and platform rows (the dated rows the probe measured, by id) each certified process3 release ran at, `{"releases": [{"release", "at", "product": {...}, "platform_rows": [...]}]}`; a figure is inside when it is at most the largest a release ran at. Empty today: it fills at the first certified release (Bob, 3 Nov: everything released so far is development only).
- `shims/process-dev-release.yml`: the development release, on a `workflow_dispatch` on the tranche with inputs `version` and `commit` (BOB's; `release dev` prints the `gh workflow run` command), so the file, commit, config and pin all come from the tranche. Bob's settings: an environment `p3dev-release` whose deployment branch rule allows only the tranche, holding the secret `release.sign_secret` names. Development only: there is no public release, and nothing here publishes or promotes one. Job checks (contents: read) installs the lock files as the gate does and runs each `release.checks` argv within its own timeout, without the GitHub tokens; job assemble (contents: read) runs `release.assemble`, which must write the release files to `release.out`, and uploads them; job publish (contents: write, environment `p3dev-release`) runs no product code: it refuses unless `github.ref` is the tranche the default branch's config names (`tranche` when it has none), the dispatched commit's config names the same tranche, and the commit is the `commit` input; it checks the version input, packs `release.out` into one archive `<product>-p3dev-<version>.tar.gz` (the repository's name; paths kept, so two files may share a base name) and writes `SHA256SUMS` over it, signs only when `release.sign_secret` names a secret (the Ed25519 signature of SHA256SUMS, `SHA256SUMS.sig`, the PEM key in that secret), pushes the tag `p3dev-<version>` at the commit itself by the API (an existing tag fails the run and is never moved; a draft has no tag until published), and creates a draft release, never published and never marked latest, with the archive, SHA256SUMS and, when signed, SHA256SUMS.sig as its only assets and the checks' results in its body; it prints the draft's link. Only a run whose checks and assemble all pass gets a tag and a draft. A tag left by a run that failed after making it uses up that version (tags are never deleted): pass another `--version`. Hidden files in `release.out` are not uploaded, so not archived. A plain pull request may add it only as this shim byte for byte at the pin (merge's workflow rule). setup check's shim-drift requires it only of a product whose config has `release`, or that carries it.
- `shims/CLAUDE.process.md`: the process lines a product's CLAUDE.md carries below Bob's approvals, which the tool never writes (TXT-1): the pin, the one fetch command (`{tranche}` is the tranche's name), and where the role prompt comes from.
- `rulebooks/<role>.md`: one rulebook per role (bob, root, watcher, job, worker), at most ten rules and three trimmed principles, each citing its Ledger line or Bob's word and naming what holds it or saying nudge (TXT-3, TXT-4, TXT-6). Not a shim and not a skill: a product reads them in its pin at `.process/rulebooks/`, and each role's prompt (and the review brief) names its own file, because a skill loads by its description, not by role, and ENF-1 allows no new hook (TXT-5). `tool/test/rulebooks.test.mjs` holds the caps.
- `shims/settings.hooks.json`: the only hooks a product's `.claude/settings.json` may carry (ENF-1); setup check's `shim-drift` fails any other.

## Commands

Run from a product checkout with the pinned clone at `.process/`: `node .process/tool/p3.mjs <command>`.

Every act that gives BOB new work ends with the wake of BOB as its last line, `next act: wake BOB with \`p3 send bob "<what>: run status" --from <sender>\``, runnable as printed, for the session that took it to deliver with send_message: a pin move's merge into the tranche (never into a working branch), `layer close`, `tranche open --record` that passes it and `tranche open --check` when open, `notice triage --record` that records a verdict, and a job's `job complete` and pushed `block` (from `job-<id>`). The sender of BOB's own acts (`merge --plain`, `layer close`, `tranche open`, `notice triage --record`) is `--as <role>`, or `--as <session id>` read from the addresses; without it, the role addressed to the calling session (the container's session id), else BOB, which is awake, and no wake is printed. A wake routes nothing. ROOT's hourly sweep is the backstop. A report or question unanswered in `targets.decision_minutes` (default 30) is escalated as the BOB and job rulebooks say, and `status --role bob` lists each such report to BOB as `unanswered <from>-<n> <age>m (target <m>)`, ahead of next work.

## The review-round limit

`merge` holds it (build I, 3 Nov). Round 1 is the two fresh reviews; round 2 is the one fix pass and its confirming re-review of the fix. A reviewed merge states its rounds (`--rounds 1` or `--rounds 2`) and records them: in the merge row for a job, in the merge commit's message for a plain merge. A third round or more is refused unless the command names the decision that allowed it (`--decision "<who decided, and why>"`), which is recorded with the rounds. A merge with `--no-review` has no rounds, and naming both `--reviewed` and `--no-review` is refused. The rounds are as the command states them: the tool cannot see reviews run by subagents, so a count stated wrongly on purpose is held by the record it leaves, not by the tool.

## Coordinator guidance

- Run each outward act as its own command, never chained.
- Run `start check` first in every session; if it fails, act on nothing, send both SHAs to the starter and end.
- Record every refusal a session reports with `metrics refusal`; when `status` prints REFRESH for a session, start a fresh one to replace it.

## Onboarding

Onboarding is the plain pull request into the tranche that adds `process/config.json`. The tool makes no exception for it (build J): a config that sets `process_repo`, `tranche` or anything under `"approvals"` (its `owner` included) to other than the defaults needs Bob's word, as at any other time. Checklist line for Bob to confirm once per product: the repository is owned by a person, not an organization and never the sessions' own account; `approvals.owner` names that person (or is left out, meaning `neobobkrause`); the tranche is named `tranche` (or Bob sets another name himself); and `process_repo` is left out or set by Bob.

## The approvals block

A commit that changes the approvals block is accepted only when it is the owner's own commit through GitHub's website, or leaves the block equal to the one the owner's website commit last set on the tip of `origin/main`, `origin/<tranche>` or the base (one `git log` of the file per ref finds the commit that set each tip's block; of those that are the owner's, the newer by committer date counts). So a merge of main into the tranche that puts back main's older block is refused. A merge may also carry the block the owner had set as one of its parents saw it, when the head ends on the current owner block, so a job or release spanning two owner edits passes. A commit already on main or the tranche is not judged again. The setup check reads the same rule: the tranche's block must be that block, so an owner's website edit on main alone reads missing, and stops job starts, until main is merged into the tranche. A product whose block was never set by an owner website commit has every merge that carries a block refused until the owner sets it once on the website. An owner's approvals pull request is brought up to date by the owner on the website, not by a session's merge, which is refused until the owner's block reaches the tranche.

## Known limits

The tool's checks hold against mistakes (a session editing settings, touching another module, resolving a merge with an old copy, merging red or stale, moving the pin somewhere unreleased) and against outsiders' pull requests from forks. They do not chase a session that deliberately attacks them: deliberate attacks by a session with Write access are held by GitHub's walls (rulesets, required checks, no force-push or deletion, permissions), not by the tool. So these are left alone: approval text carried into CLAUDE.md through an `@import` of another file, or through a symbolic link put in place of the approvals file; code outside the guarded paths that a hook or a workflow runs; process3's `ci.yml` running the head's code before its record step (the required record check runs from main); and local actions a workflow uses from the repository itself. A commit made through GitHub's API with the owner's own token looks like the owner's website commit, so sessions must never hold the owner's token. Not yet probed: whether a commit a session authors with the owner's public email, then rewritten and signed by GitHub, reads as the owner's website commit.

Held only by GitHub's walls since build J (3 Nov):
- Required checks on `merge --plain`: the tool waits for them to finish, and GitHub's ruleset decides whether they are green, from which app, on which workflow copy, and whether the head must be up to date. The tool no longer refuses a second open pull request from the same head.
- An owner's old approvals draft newer than everything on main and the tranche: the record check judges each commit against the blocks on those tips, not against the dates of every block the owner ever set.
- Onboarding corner cases (an organization-owned repository, a repository the sessions' own account owns, a tranche of another name): Bob's checklist line above.
- The gate row job post writes: only the fields it prints are checked; merge trusts a row only when the run's own artifact holds the same row.

Known limit of the start check:
- `start check` compares the approvals block in the checkout's file with the tip's, as the session loaded it from disk at its start; a session that edits the file after its start check is held by the record check, not by this.
